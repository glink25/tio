# 本地编辑器与外部 Agent 联动：一手来源笔记

调研时间：2026-10-29。本文记录已查阅的官方文档与由此得到的设计建议，不代表已安装、运行或验证这些产品。主方案应结合 Tio 当前运行时与 provider 实现确定。

## 已核实的产品模式

| 产品 / 标准              | 官方资料确认的能力                                                                                                                                                                                                                                                                                                     | 对 Tio 的启示（推论）                                                                                           |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Obsidian 文件 vault      | 笔记是本地文件夹中的 Markdown；允许其他编辑器修改，应用刷新外部变化。[数据存储](https://obsidian.md/help/data-storage)                                                                                                                                                                                                 | 普通文件使 agent 的检索、批量重写和脚本天然可用；但不能由此推导复杂对象数据库也适合无校验直写。                 |
| Obsidian CLI             | 官方 CLI 支持读写、搜索、查询 Bases、执行命令等；连接运行中的应用，未运行时启动应用。[CLI 文档](https://obsidian.md/help/cli)                                                                                                                                                                                          | 文件访问与语义命令可以并存。CLI 能让 agent 调用领域能力，也避免必须操作 GUI。                                   |
| 思源 HTTP API            | 通过块 ID 增删改移；更新可输入 Markdown 或 DOM；`lockType` 可拒绝解析后块类型变化，非法父子结构始终拒绝。[官方 API](https://raw.githubusercontent.com/siyuan-note/siyuan/master/docs/API.md)                                                                                                                           | 富文本无需退化成 Markdown 文件，外部工具可以提交易写的片段，由应用解析并维护结构约束。                          |
| Anytype API v1           | 提供按空间寻址的对象读写，正文支持 Markdown，并管理类型与属性；删除对象为归档。[对象指南](https://developers.anytype.io/docs/guides/get-started/objects/)                                                                                                                                                              | 外部 agent 接入对象模型，不必理解底层数据库或同步文件。                                                         |
| Anytype API v2（预发布） | 单对象 JSON 文档与原子批量 PATCH；提供 ETag 条件写、幂等键、dry run 和 schema/validate；部分读取及只读 Markdown 不允许作为整文覆盖写入。[v2 官方说明](https://developers.anytype.io/docs/reference/v2/anytype-api/)                                                                                                    | 很贴近 Tio 的需求：易编辑的公开表示，加并发检查和验证边界。它是设计参考，不能作为稳定生产能力或行业共识的证明。 |
| Anytype 官方 MCP         | 包装本地 API；`expected_etag` 映射条件写，`request_key` 映射幂等键；不自动重试或移除失败的前置条件；保留 schema 与 dry run。[官方仓库](https://github.com/anyproto/anytype-mcp)                                                                                                                                        | MCP 应是核心能力的薄适配层，不能另建一套数据写入语义。                                                          |
| VS Code WorkspaceEdit    | 纯文本 edits 按全有或全无应用；混有创建/删除资源的编辑在失败时停止后续操作。文件从磁盘被外部修改与应用内文件事件不是一回事。[官方 API](https://code.visualstudio.com/api/references/vscode-api)                                                                                                                        | “批量”不自动等于磁盘事务。Tio 必须单独定义事务的可见性、失败与恢复保证。                                        |
| MCP 工具标准             | 工具可以声明输入/输出 schema 并返回结构化结果；业务工具失败应通过 `isError` 呈现，使模型能看到并修正。[工具规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx)、[官方 SDK 错误说明](https://ts.sdk.modelcontextprotocol.io/v2/servers/errors) | 校验结果应包含错误码、对象与字段位置、修复提示；不能让 agent 仅凭自然语言判断是否提交成功。                     |

## 对“自由编辑文件夹 + 草稿区”的设计建议

以下是针对 Tio 的推论，并非上述产品共同承诺的现成方案。

1. **给 agent 一份可修改的工作副本。** 将一批对象按稳定 ID 导出到独立草稿目录，记录基线版本、对象集合和协议版本。运行中的正式空间不读取草稿半成品。草稿中 JSON 暂时不合法应只产生诊断，不影响正式文档。
2. **把验证与提交拆开。** `validate` 可反复运行，`diff` 展示语义变化，`apply` 必须再次验证草稿内容与基线。验证成功不代表之后的文件仍是同一份，故提交应绑定内容摘要，且原子地做前置条件检查。
3. **至少检查三层。** 解析与字段类型；空间内 ID、父子树、数据库字段、关系与附件等完整性；自动化目标及执行边界。结构合法只能防解析损坏，不能判断内容是否符合用户意图，仍需要预览、撤销或历史快照。
4. **保留未知字段与不透明块。** 可读 Markdown 是阅读与片段编辑接口；遇到无法表达的内容，应保留原始对象，不能默默经过 Markdown 整文往返。命令应尽量修改指定字段或块，不要求模型重写整个对象。
5. **使用统一写入入口。** CLI、MCP、草稿导入和 UI 都调用同一领域命令与运行时。草稿目录仅为待提交输入，不是新的保存队列，也不成为另一个长期真相源。
6. **给并发清晰的拒绝行为。** Agent 从基线读取后，用户可能继续键入。提交遇到基线变化或尚未确认的输入应返回结构化冲突，允许重新读取或重新生成补丁；不要自动丢弃条件写再覆盖。
7. **定义事务边界。** 单文件 rename 无法保障跨多个文件、附件和索引的事务。可选择运行时内一次提交加可恢复日志，或 provider 支持的快照切换，但不要仅凭“先全部校验”宣称提交具备原子性。
8. **自动化有两种不同能力。** 编辑自动化定义与执行自动化必须区分。草稿验证与预览不执行副作用；正式导入是否触发规则需由提交语义明确决定，避免文件导入意外批量触发。
9. **访问限制需要实现边界。** 把正式目录写权限直接给终端 agent 后，约定“只改草稿”不是硬隔离。若要求强保证，应由宿主持有正式数据写权限，agent 仅能访问草稿与受控命令；否则产品应准确称为受校验的推荐工作流。

## 仍需由项目验证的问题

- 当前 provider 的批量提交、崩溃恢复与外部文件刷新实际保证如何；浏览器和 CLI 是否会同时持有同一空间。
- 当前校验器是否只检查信封结构，还是会深入富文本、数据库和自动化引用。
- 自动化事件来自命令提交还是文件快照差异；外部批量导入如何避免重复执行。
- 现有撤销是否仅存于当前进程；跨会话草稿提交需要怎样的历史和恢复记录。

不能由所查资料断言“所有主流应用都采用草稿区”、MCP 自带数据事务、Markdown 能无损表达任意富文本，或文件监听能解决多人并发。
